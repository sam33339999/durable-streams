## 1. 架構概覽

```
用戶端（TS / Python / Go / Elixir / .NET / Swift / PHP / Java / Rust / Ruby）
         │
         ▼  HTTP（GET / POST / PUT / DELETE / HEAD）
┌────────────────────────────────────────┐
│           Caddy HTTP Handler           │
│         （packages/caddy-plugin）       │
├────────────────────────────────────────┤
│              Store Layer               │
│  ┌─────────────────┬─────────────────┐ │
│  │  MemoryStore    │   FileStore     │ │
│  │  （開發/測試用）  │  （正式環境）    │ │
│  └─────────────────┴─────────────────┘ │
└────────────────────────────────────────┘
         │                    │
    （揮發性記憶體）   bbolt 元資料 DB
                       + .seg 分段檔案
```

伺服器架構沒有分散式協調層或共識協議。這是一個**單節點**服務，可選搭配檔案儲存後端以提供持久化能力。

## 2. 內部資料結構與演算法

### 2.1 偏移量（Offset）— 可依字典序排序的位置

串流中的每個位置都以 `Offset` 結構表示：

```
格式：「RRRRRRRRRRRRRRRR_BBBBBBBBBBBBBBBB」
       │── 16 位數字 ──│ │── 16 位數字 ──│
            ReadSeq          ByteOffset
```

| 欄位         | 說明                                              |
|--------------|---------------------------------------------------|
| `ReadSeq`    | 保留供未來日誌輪替使用（目前始終為 `0`）            |
| `ByteOffset` | 已寫入的**有效載荷資料**累計位元組數（不含框架標頭）|

使用零填充十進位表示法，讓偏移量可直接以**字典序字串比對**進行大小比較，無需整數解析。這對 HTTP 範圍語義以及用戶端將最後一次讀取偏移量以純字串形式儲存來說非常重要。

特殊值：

| 偏移量字串 | 含義 |
|-----------|------|
| `"0000000000000000_0000000000000000"` | 串流起點（重播所有訊息） |
| `"-1"` | 串流起點的別名 |
| `"now"` | 略過所有歷史資料；僅訂閱未來新寫入的訊息 |

### 2.2 分段檔案（Segment File）— 僅附加的長度前置日誌

串流資料以二進位**分段檔案**（`data.seg`）形式持久化：

```
┌────────────────────────────────────────────────────────────┐
│  [4 位元組 BE 長度] [有效載荷位元組]                         │
│  [4 位元組 BE 長度] [有效載荷位元組]                         │
│  ...                                                        │
└────────────────────────────────────────────────────────────┘
```

- 每則訊息前有 4 位元組大端序（Big-Endian）無號整數，表示有效載荷長度。
- 訊息直接串接，無分隔符或校驗碼。
- 單則訊息最大限制為 **64 MB**（`MaxMessageSize = 64 * 1024 * 1024`）。
- `Offset` 中的 `ByteOffset` 是**下一則訊息有效載荷起始位置**的累計資料位元組數（非檔案位元組數）。
- 隨機存取透過 `SeekToOffset(byteOffset)` 實現：由於偏移量追蹤的是資料位元組而非檔案位元組，讀取端需從頭掃描以找到正確的檔案位置。對於大型串流，應避免在熱路徑中頻繁跳轉到任意舊偏移量。

**JSON 模式**：當 `Content-Type` 為 `application/json` 時，每則儲存訊息對應一個 JSON 值。寫入串流的陣列會被**展平**（每個元素成為獨立訊息），讀取時再將所有訊息包裝回 `[…]` 陣列格式。

### 2.3 元資料儲存——bbolt（嵌入式鍵值資料庫）

檔案儲存後端使用 **bbolt**（純 Go 實作的嵌入式 B-tree 資料庫）來儲存串流元資料：

```
bbolt 檔案路徑：{dataDir}/metadata/metadata.db
```

每筆串流記錄包含：

| 欄位            | 型別                  | 說明                           |
|-----------------|----------------------|--------------------------------|
| `Path`          | string               | 串流 URL 路徑（主鍵）           |
| `ContentType`   | string               | 建立後即鎖定，不可更改           |
| `CurrentOffset` | Offset               | 最新尾端偏移量                  |
| `ExpiresAt`     | *time.Time           | 絕對到期時間（選填）             |
| `TTLSeconds`    | *int64               | 相對 TTL 秒數（選填）           |
| `Producers`     | map[id]→ProducerState | 冪等生產者追蹤狀態              |
| `Closed`        | bool                 | 串流是否已封閉                  |
| `ClosedBy`      | *ClosedByProducer    | 封閉串流的生產者資訊            |

bbolt 事務提供**序列化寫入搭配並行讀取**，對每個鍵提供 ACID 語義。元資料儲存在啟動時會完整載入記憶體快取（`metaCache`），以實現低延遲讀取。

### 2.4 檔案描述符池——LRU 淘汰機制

為每次讀寫都開啟新的檔案描述符代價高昂。Durable Streams 維護了兩個 LRU 池：

| 池             | 方向 | 底層結構                           |
|----------------|------|------------------------------------|
| `FilePool`     | 寫入 | `map[path]→entry` + `list.List`（LRU）|
| `ReaderPool`   | 讀取 | 相同模式                           |

當池中條目數達到設定上限（`max_file_handles`，預設為 **100**）時，**最近最少使用**的項目會被關閉並淘汰。下次存取該檔案時會自動重新開啟，對呼叫端透明。

TypeScript 參考伺服器使用 **SIEVE 快取**取代純 LRU——這是一種較新的淘汰演算法，對新項目有「試用期」機制，在混合工作負載下有更高的命中率。

### 2.5 記憶體儲存——Map + Channel 通知機制

```
MemoryStore
├── streams: map[path] → memoryStream
│   ├── metadata: StreamMetadata
│   ├── messages: []Message        ← JSON 模式
│   └── data: []byte               ← 二進位模式
│
├── longPoll: longPollManager
│   └── waiters: map[path] → []chan struct{}
│
└── producerLocks: map["path:producerId"] → *sync.Mutex
```

長輪詢（Long-poll）用戶端阻塞在 `<-channel` 上。當新訊息寫入時，寫入端呼叫 `notify(path)`，以非阻塞方式向所有等待通道發送訊號，立即喚醒等待中的用戶端。

### 2.6 冪等生產者狀態機

每個生產者（透過請求標頭 `Producer-Id`、`Producer-Epoch`、`Producer-Seq` 識別）都會按串流分別追蹤狀態：

```
State: { Epoch: int64, LastSeq: int64, LastUpdated: unix-timestamp }
```

每次寫入都會驗證以下規則：

| 條件                                   | 結果                            |
|----------------------------------------|---------------------------------|
| `epoch < state.Epoch`                  | `ErrStaleEpoch`（殭屍節點防護） |
| `epoch > state.Epoch`                  | 接受新紀元；序列號重置為 0      |
| `seq == state.LastSeq`                 | 重複訊息 → `204 No Content`     |
| `seq == state.LastSeq + 1`             | 新訊息 → 接受                   |
| `seq > state.LastSeq + 1`             | `ErrProducerSeqGap`（序列號缺口）|

此機制在**單一生產者紀元（epoch）內提供精確一次（exactly-once）語義**，無需伺服器與其他實例協調。

## 3. 資料如何寫入與儲存

### 3.1 記憶體儲存的寫入流程

```
POST /v1/stream/my-topic  →  MemoryStore.Append()
   │
   ├─ 取得每個生產者的互斥鎖（如有生產者標頭）
   ├─ 驗證生產者狀態（紀元/序列號檢查）
   ├─ 附加至 messages 切片（JSON 模式）或 data 位元組切片（二進位模式）
   ├─ 更新 metadata.CurrentOffset
   ├─ 釋放互斥鎖
   └─ 通知長輪詢等待者（非阻塞 channel 發送）
```

所有操作均在記憶體中完成，**無任何 I/O**。程序結束後，資料立即消失。

### 3.2 檔案儲存的寫入流程

```
POST /v1/stream/my-topic  →  FileStore.Append()
   │
   ├─ 取得每個生產者的互斥鎖
   ├─ 鎖定 metaCacheMu（寫入鎖）
   ├─ 從 metaCache 驗證生產者狀態
   │
   ├─ 從 dirCache 解析分段檔案路徑
   ├─ 從 FilePool 取得或開啟寫入器（LRU 管理）
   ├─ 將長度前置訊息寫入分段檔案
   ├─ 呼叫 file.Sync() / fdatasync()   ← 持久化保證
   │
   ├─ 以 bbolt 事務原子性更新元資料：
   │    ├─ UpdateOffset（新偏移量）
   │    └─ UpdateAppendState（生產者狀態）
   │
   ├─ 更新記憶體中的 metaCache
   ├─ 釋放 metaCacheMu
   ├─ 釋放生產者互斥鎖
   └─ 通知長輪詢等待者
```

每次寫入後的 `Sync()` 呼叫確保資料在返回 HTTP 200 給用戶端**之前**已寫入持久儲存。這讓附加操作**預設即具備崩潰安全性**，代價是每則訊息需執行一次 fsync，會增加寫入延遲。

### 3.3 磁碟上的串流目錄結構

```
{dataDir}/
├── metadata/
│   └── metadata.db          ← bbolt 資料庫（所有串流元資料）
└── streams/
    ├── %2Ftopic-a~1700000001~a3f9b2/
    │   └── data.seg
    └── %2Ftopic-b~1700000002~c8e1d4/
        └── data.seg
```

目錄名稱格式為 `{url_encoded_path}~{unix_timestamp}~{random_hex}`。隨機後綴實現了**安全的非同步刪除**：當串流被刪除後立即在同一路徑重新建立時，新串流會獲得全新目錄，舊目錄則在背景非同步回收，不會產生衝突。

### 3.4 啟動時的崩潰恢復

檔案儲存初始化時會執行以下步驟：

1. 開啟 `metadata.db`，將所有串流記錄載入 `metaCache` 和 `dirCache`。
2. 對每條串流而言，分段檔案是實際資料的**可信來源（source of truth）**。若 bbolt 與分段檔案不一致（例如崩潰發生在事務中途），以分段檔案為準。
3. `ScanSegment()` 可依序讀取分段檔案，在最後一則完整訊息處停止，驗證檔案完整性——崩潰造成的不完整訊息會被靜默丟棄。

## 4. 儲存空間不足時的行為

### 4.1 單則訊息大小限制

伺服器強制執行每則訊息 **64 MB** 的硬性上限（`MaxMessageSize`）。超過限制的有效載荷在任何資料寫入前即以 `ErrMessageTooLarge` 拒絕。

### 4.2 磁碟空間不足（檔案儲存）

當底層磁碟沒有可用空間時：

- 對分段檔案的 `WriteMessage()` 呼叫會返回 OS 級 I/O 錯誤。
- 此錯誤向上傳遞，以 HTTP 500 回應返回給用戶端。
- 串流狀態**不會損壞**：未完成的寫入不會被提交。
- bbolt 元資料更新不會被嘗試，元資料保持一致。
- **不會自動淘汰舊串流**。管理員必須手動介入，釋放磁碟空間或刪除舊串流（透過 `DELETE /v1/stream/{path}`）。

### 4.3 記憶體不足（記憶體儲存）

記憶體儲存對串流數量或總位元組數**沒有內建容量限制**。增長僅受可用 RAM 限制。當 Go 運行時記憶體耗盡時，程序會被 OS 強制終止（OOM Kill）。

緩解措施：
- 對每條串流設定 `Stream-TTL`，使其自動過期。
- 對資料總量難以預測的工作負載，改用檔案儲存。
- 監控 RSS / 堆積大小，在耗盡前發出警報。

### 4.4 檔案描述符耗盡

當同時活躍的唯一串流路徑數超過 `max_file_handles` 限制時，LRU 池會淘汰最近最少使用的描述符。這對呼叫端透明：下次存取時只需重新開啟檔案，不會返回錯誤。

但若某次突發流量同時觸碰數千條唯一串流，淘汰成本（關閉 + 重新開啟系統呼叫）可能成為瓶頸。應根據並行存取規模調大 `max_file_handles`。

### 4.5 TTL 到期機制

串流支援兩種到期方式：

| 標頭                        | 範例                                      | 行為                        |
|-----------------------------|-------------------------------------------|-----------------------------|
| `Stream-TTL: <秒數>`        | `Stream-TTL: 86400`                       | 建立後 24 小時到期           |
| `Stream-Expires-At: <RFC3339>` | `Stream-Expires-At: 2026-01-01T00:00:00Z` | 在指定絕對時間到期         |

已到期的串流返回 `404 Not Found`。磁碟上的刪除採用延遲回收（下次存取時觸發），或由設定 `cleanup_interval` 的背景清理協程執行。

## 5. 自架服務清單

### 5.1 儲存模式選擇

| 使用場景                      | 建議儲存模式         |
|-------------------------------|---------------------|
| 本地開發 / CI 測試            | `memory`（預設）    |
| 暫存環境 / 短暫資料           | `memory` 搭配 TTL   |
| 正式環境 / 需要持久化         | `file`              |

### 5.2 最小化正式環境 Caddyfile

```caddyfile
{
    admin off
}

:4437 {
    route /v1/stream/* {
        durable_streams {
            data_dir /var/lib/durable-streams

            # 根據工作負載調整以下參數：
            max_file_handles 200
            long_poll_timeout 30s
            sse_reconnect_interval 60s
        }
    }
}
```

### 5.3 設定參數參考

| 參數                     | 預設值 | 說明 |
|--------------------------|--------|------|
| `data_dir`               | *（未設定則使用記憶體儲存）* | 檔案儲存的資料路徑。**正式環境必須設定此項。** |
| `max_file_handles`       | `100`  | LRU 池中最大開放檔案描述符數量。串流並行數較多時應增加此值。 |
| `long_poll_timeout`      | `30s`  | 長輪詢請求等待新資料的最長時間，逾時後返回空的 200 回應。 |
| `sse_reconnect_interval` | `60s`  | SSE 連線的循環週期，用於清除閒置連線。 |

### 5.4 部署檢查清單

- [ ] **持久化儲存**：將 `data_dir` 設定為持久化磁碟卷的路徑（非 tmpfs 或容器臨時層）。
- [ ] **磁碟空間**：估算串流總量，確保磁碟有足夠餘裕。串流不會自動壓縮，除非被刪除或到期。
- [ ] **檔案描述符限制**：檢查 OS 限制（`ulimit -n`）。池中每個開放的檔案描述符都計入此限制。建議系統限制至少為 `max_file_handles × 2 + 1024`。
- [ ] **備份**：`data_dir` 包含 `metadata/metadata.db`（bbolt）和 `streams/*/data.seg`。請備份整個 `data_dir` 目錄。由於 bbolt 採用 MVCC 寫時複製，在伺服器執行中複製資料庫檔案是安全的；但若要確保 bbolt 元資料與分段檔案完全一致，應進行檔案系統快照或在複製前短暫停止伺服器（參見第 7.3 節）。
- [ ] **反向代理 / TLS**：使用 Caddy 自動申請 Let's Encrypt 憑證，或在前端放置 TLS 終止的負載均衡器。
- [ ] **CORS**：伺服器預設發送開放 CORS 標頭（`Access-Control-Allow-Origin: *`）。如有需要，請在反向代理層限制此設定。
- [ ] **認證鑑權**：協議本身無內建認證機制。請在網路層或反向代理層保護端點（例如 Caddy 的 `basicauth`、mTLS 或 API Gateway）。
- [ ] **串流 TTL**：對不希望無限累積的串流，務必設定 `Stream-TTL` 或 `Stream-Expires-At`。
- [ ] **清理間隔**：啟用 `cleanup_interval 1h`（或適當間隔）的背景清理，以自動從磁碟移除已到期的串流。
- [ ] **監控**：監控磁碟使用量、程序 RSS、檔案描述符數量及 HTTP 錯誤率。
- [ ] **優雅停機**：向 Caddy 程序發送 `SIGTERM`。Handler 的 `Cleanup()` 方法會關閉所有檔案描述符並刷新 bbolt 資料庫。

### 5.5 建議目錄結構

```
/var/lib/durable-streams/   ← data_dir
    metadata/
        metadata.db
    streams/
        ...
/etc/caddy/
    Caddyfile
/var/log/caddy/             ← Caddy 結構化 JSON 日誌
```

## 6. 記憶體模式與檔案模式的持久化行為差異

### 重啟後資料是否保留？

| 儲存模式          | 重啟行為 |
|-------------------|----------|
| **記憶體儲存**    | **所有資料立即遺失。** 記憶體中的 Map 被丟棄，沒有自動「刷寫至磁碟」或預寫式日誌（WAL）。 |
| **檔案儲存**      | 資料在重啟後持續保存。伺服器啟動時重新讀取 `metadata.db` 和分段檔案，從最後成功同步的偏移量繼續。 |

### 預設是記憶體模式嗎？

**是的。** 若 Caddyfile 中未設定 `data_dir`（或執行 `durable-streams-server dev`），伺服器使用記憶體儲存。這是刻意設計：讓零設定體驗快速且無依賴。

**若需啟用持久化**，請在 `durable_streams` 區塊中加入 `data_dir /your/path`。

### 為何記憶體模式不提供自動日誌持久化？

記憶體儲存刻意保持簡單且記憶體分配高效。對需要持久化的工作負載，檔案儲存才是正確選擇。混合兩者（例如先緩存記憶體再定期刷寫）會引入部分持久化語義，使崩潰恢復的推理變得複雜。

## 7. 運維注意事項

### 7.1 並行模型

| 機制                           | 範圍                              | 用途 |
|--------------------------------|-----------------------------------|------|
| `producerLocks`（每個生產者的互斥鎖） | `"{path}:{producerId}"` 鍵 | 序列化紀元/序列號驗證與附加操作，防止亂序 HTTP 請求造成假間隙 |
| `metaCacheMu`（RWMutex）       | 整個元資料快取                    | 允許並行讀取元資料；寫入時才加獨佔鎖 |
| `longPollManager.mu`（Mutex）  | 等待通道 Map                      | 保護通道的注冊/取消注冊操作 |
| bbolt 事務                     | 元資料資料庫                      | 單一寫入者；透過 MVCC 支援並行讀取 |

### 7.2 崩潰恢復詳情

| 故障場景 | 恢復結果 |
|----------|----------|
| 在分段檔案**寫入過程中**崩潰 | OS 可能已寫入部分資料。重啟後 `ScanSegment()` 停在最後一則完整訊息。bbolt 未更新 → 偏移量未推進。用戶端重試寫入；伺服器接受為新訊息（或若使用了 `Producer-Seq` 則視為重複）。 |
| 分段檔案寫入後但 **`Sync()` 之前**崩潰 | 資料可能未持久化到磁碟。bbolt 未更新 → 同上。 |
| **`Sync()` 後**但 **bbolt 提交前**崩潰 | 分段檔案有資料；bbolt 未反映新偏移量。下次寫入時 `ScanSegment()` 會發現多餘資料並修正偏移量。 |
| bbolt 檔案損壞 | bbolt 使用寫時複製 B-tree 與預寫式日誌，可從大多數部分寫入中恢復。分段檔案仍有效。 |
| 分段檔案尾端部分截斷 | `ScanSegment()` 跳過不完整的尾端訊息。截斷點之前的資料完全可恢復。 |

### 7.3 備份策略

1. **熱備份（不停機）**：在伺服器執行時複製整個 `data_dir`。bbolt 使用 MVCC，複製中的快照是該時刻的一致性視圖。分段檔案為僅附加模式，隨時複製均安全。
2. **冷備份（完全一致）**：停止伺服器（`SIGTERM`），複製 `data_dir`，再重新啟動。這是確保 bbolt 元資料與分段檔案完全同步的唯一方法。
3. **還原**：以備份副本替換 `data_dir`，重新啟動即可。

### 7.4 無內建日誌輪替或資料壓縮

分段檔案會無限增長。目前**沒有內建的日誌輪替或資料壓縮**機制。管理磁碟使用量的方式：

- 設定 `Stream-TTL`，讓串流自動刪除。
- 顯式呼叫 `DELETE /v1/stream/{path}` 移除串流並釋放磁碟空間。
- 使用 `cleanup_interval` 背景清理，自動移除已到期的串流。

### 7.5 規模限制

伺服器**僅支援單節點**，無複製、分片或分散式共識能力。實際限制如下：

| 資源             | 典型瓶頸 |
|------------------|----------|
| 寫入吞吐量       | 每則訊息一次 `fsync()`；機械硬碟受 IOPS 限制，高頻寫入建議使用 SSD。 |
| 並行串流數       | `max_file_handles`。增加此值並確認 OS `ulimit` 相應提高。 |
| 總儲存資料量     | 可用磁碟空間。 |
| 長輪詢扇出數     | 每個等待用戶端持有一個 goroutine 和一個 channel。若單一串流的長輪詢客戶端超過萬級，可能需要 pub-sub 中介層。 |
| bbolt 寫入競爭   | bbolt 同時只允許一個寫入者。高並行混合讀寫工作負載可能在元資料層產生排隊。 |

### 7.6 監控清單

| 監控指標                        | 原因 |
|--------------------------------|------|
| `data_dir` 磁碟使用量          | 串流不會縮小；磁碟耗盡會阻塞**新寫入**（HTTP 500）——現有資料不會遺失，但服務品質下降 |
| 程序 RSS 記憶體                | 記憶體儲存：無限增長 |
| 開放檔案描述符數量              | 必須低於 OS 的 `ulimit -n` |
| HTTP 500 / 507 錯誤率          | 表示儲存層發生錯誤 |
| 長輪詢超時率                   | 超時率高可能表示生產者已停止寫入 |
| `metadata.db` 檔案大小         | 過大表示串流數量多或生產者狀態 Map 龐大 |

### 7.7 常見運維問答

**問：可以同時啟動多個伺服器實例指向同一個 `data_dir` 嗎？**  
不行。bbolt 在啟動時會獲取獨佔檔案鎖。第二個實例啟動會直接失敗。目前不支援水平擴展。

**問：如何刪除單條串流？**
```
DELETE /v1/stream/{path}
```
此操作同時移除分段檔案和 bbolt 記錄。磁碟空間立即被回收。

**問：刪除串流後，用戶端重新使用相同路徑會怎樣？**  
向已刪除路徑發送 `POST` 會建立新串流。新串流獲得全新目錄（帶有不同的隨機後綴），因此不會有讀取到舊串流歷史資料的風險。

**問：不使用用戶端函式庫，如何直接查看串流內容？**
```bash
curl http://localhost:4437/v1/stream/my-topic
```
此命令返回所有已儲存的訊息。若需即時串流，加上 `?live=sse` 或 `?live=long-poll`。

**問：可以變更現有串流的 `Content-Type` 嗎？**  
不行。Content-Type 在建立時鎖定，每次附加時都會驗證。嘗試在相同路徑以不同 Content-Type 建立串流會返回錯誤。

**問：生產者文件提到「epoch（紀元）」，這是什麼用途？**  
當生產者程序重新啟動時，它會遞增自己的紀元號。伺服器將此作為防護令牌（fencing token）：來自舊程序實例（使用較低紀元）的所有在途請求都會被拒絕，防止殭屍生產者在重啟後寫入過時資料。

**問：網路分區期間寫入的訊息在重連後會重播嗎？**  
用戶端以最後一次讀取的偏移量作為恢復點。若用戶端斷線期間伺服器持續接收新訊息，用戶端重連後從已儲存的偏移量繼續，即可依序收到所有遺漏的訊息。
